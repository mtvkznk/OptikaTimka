## Що потрібно знати наступному виконавцю

Пакет переносимого контексту додано 22 листопада: кореневий AGENTS, шість
пов'язаних документів, індекс у README та повний приклад admin grant у
`prod.env.example`. Стару workspace-інструкцію перенаправлено сюди, історичні
локальні звіти позначено як такі. Для цього документаційного оновлення
перевірено локальні посилання/шляхи/ревізії, шаблони секретів, ігнорування приватної
картки та синтаксис PowerShell-прикладів. Серверний runtime не змінювався.

- Google — єдиний вхід на сайт. Telegram — лише інструмент прив'язаних адмінів.
- Перенесення розробки на інший ПК не включає перенесення сервера.
- Ручний/онлайн запис та бот мають одну базу й однакову перевірку зайнятості.
- Не видаляти пацієнтів як «тестових» за старими повідомленнями чату. Історичне
  очищення не є постійним дозволом на видалення нових даних.
- Не відтворювати старий список admin emails із чату: поточні grants у
  захищеному env. Зміна одного admin grant не повинна затерти інші.
- Зауваження «сервер вимкнений», «ще не деплоїти», «84 тести» зі старої
  workspace-нотатки описували минулі етапи, а не поточний стан.
- Старі `outputs/` і `work/optikatimka-setup` у папці початкового чату не входять
  у checkout. Поточний запуск/обслуговування описані переносимими документами.
- Приватні дані підключення зберігаються окремо, наприклад у локальній картці
  `optikatimka-operator.local.md`. Отримати її та доступи в оператора перед роботою
  з сервером; не публікувати в репозиторії.

## Відомі межі й відкриті операційні питання

1. Один активний прийом займає спільний ресурс для всіх послуг. Модель кількох
   паралельних лікарів/кабінетів не реалізована.
2. Графік має overrides за днями тижня, закриті календарні дати й блокування
   інтервалів. Довільних власних робочих годин конкретної дати немає.
3. Очищення Telegram обмежене відомими повідомленнями й можливостями Telegram;
   всю давню історію бот очистити не гарантує.
4. Docker Desktop recovery залежить від входу відповідного Windows-користувача;
   захист від кожного випадку недоступності мережі/живлення не обіцяється.
5. Автоматичні регулярні/off-host backups, їх retention та останній повний
   restore drill окремо не підтверджені. Перевірити перед заявою, що вони налаштовані.
6. Статичні контакти/години магазину в підвалі не синхронізовані автоматично з
   графіком послуг. Це різні дані; не правити booking seed задля підвалу.

Це перелік меж, а не затверджений план їх усунення. Обсяг нового завдання
визначається актуальним запитом користувача.

## Як залишити наступний handoff

Після суттєвої роботи оновити дату, поведінковий commit і фактичний release
окремо, schema revision, посилання на CI, виконані перевірки, незавершені питання
та потрібні зовнішні дії. Поведінкові правила змінити в BUSINESS_RULES і DECISIONS.
Не дублювати весь журнал Git; не додавати секрети або копії даних клієнтів.
